# 同名渠道兜底（一个型号挂多条上游渠道）

## 为什么要有这一层

平台目录按「显示名 + 能力」把同名模型合并成一行：`GPT Image 2.5 Sunburst` 这一行背后同时挂着
fal 和 Replicate 两条系统渠道，用户看到的是一个型号，看不到背后是谁在出图。

合并成一行之后，一条上游渠道出故障就不再只是"某个渠道不可用"：它直接等于这个型号不能用。
用户按下生成，拿到的是失败，而平台明明还有另一条同型号的渠道可用。渠道级兜底就是补这一段：
**在上游确定没有为这次请求建任务时，把这次生成换到同一行里的另一条渠道上重发。**

## 触发条件：只有"确定没建任务"才换

换渠道重发不复用幂等键——上游是另一家，键也不通用。所以判据不能是"失败了"，只能是
**上游没有为这次请求建任务**。目前只有两类失败满足：

| 证据 | 来源 | 落点状态 |
| --- | --- | --- |
| 上游明确拒单 | 401 / 402 / 403 / 404 / 429、渠道并发槽位失败 | `rejected_no_job` |
| 边缘网关连续两次都没把请求交给源站 | 502/503 且响应正文不是供应商 JSON（网关自己的错误页），重放一次同样如此 | `rejected_no_job` |

其余失败一律不换：

- **供应商自己回的 5xx**（带 JSON 正文）说明请求已经到达上游，可能已经建任务并计费；
- **超时、连接中断、504/524** 是"转出去了没等到回执"，同样可能已经建任务；
- 这些任务按既有的结算路径走：先记提交结果未确认，再由对账去问上游，问不出来就到期退款。

首次创建遇到 502/503 时本来就会就地重放一次（同一个幂等键，安全）；只有**两次都停在网关**
才会被记成"确定没建任务"。这是为了让换渠道这一步站得住脚，而不是把一次含糊的失败当成安全。

## 换到哪一条

候选必须与当前落点**同一个型号**，判定口径与前台目录一致：

1. **显示名相同**（忽略大小写与首尾空白）+ **能力相同**；
2. 优先顺序就是目录的默认落点顺序——渠道 `sort_order`；
3. 本轮任务里**每条渠道只发一次**：任务与渠道模型的落点都记在尝试行上，试过的渠道不再入选，
   两条渠道不会互相兜底成死循环；
4. **能力合同必须接得住这次参数**：比例、质量、参考图数量等按备用渠道自己的合同校验，接不住
   就不换（换过去只是把一个拒绝换成另一个更晚的拒绝）；
5. **售价必须与被扣的那一档相同**：预扣是按原渠道价目表收的，换到更贵的渠道是平台吃差价，
   换到更便宜的渠道是多收用户的钱；任一边未定价都不自动换。

## 落库的改动

失败的那一次尝试保留原样（状态、失败码、失败消息都不动），只是：

- 任务的 `channel_model_id` 与 `input_json` 里的渠道选择改写到备用渠道（`channelId`、
  `channelModelKey`、`model`、规格变体一起换，规格变体属于具体渠道，不能沿用）；
- 新增一条尝试行，`attempt_number` 递增，`dispatch_state = not_sent`，并带上备用渠道的身份。

任务日志里会留一条 `上游未受理本次请求，换同名渠道重发`，payload 是 `渠道::模型`。
用户在任务详情里看到的仍然是同一个型号，扣的也还是原来那一档的价。

## 与前台逻辑模型路由的关系

前台逻辑模型模式有自己的路由表、权重和路由健康度，换路由由 `switchTaskToNextRoute` 负责；
渠道级兜底只处理**直连系统渠道**的任务（`logical_model_id` 为空）。两条路不能互相顶掉对方的
选择，因此兜底只在直连任务上生效。

## 已知边界

- 一条渠道彻底挂掉时，后面的任务仍然会先打到挂掉的那条（失败一次再兜底），目前不做渠道级的
  前置熔断；代价是每次多一个失败往返，产物照常出。
- 承载兜底的前提是同名渠道同价。新上架的渠道若与既有渠道不同价，它不会被自动选中，需要先对齐价目。
- 兜底只对系统渠道生效；用户自定义渠道没有"同名号"的概念，不参与。
